RLE ALGORITHM
─────────────

Encoding (RLE.encode):
  Input:  Sequence of bytes [1, 1, 1, 2, 2, 3]
  Process:
    - 1 appears 3 times (run) → [255, 1, 3]
    - 2 appears 2 times (run) → [255, 2, 2]
    - 3 appears 1 time (single) → [3]
  Output: [255, 1, 3, 255, 2, 2, 3]

Decoding (RLE.decode):
  Input:  [255, 1, 3, 255, 2, 2, 3]
  Process:
    - See 255 → read (1, 3) → expand to [1, 1, 1]
    - See 255 → read (2, 2) → expand to [2, 2]
    - See 3 → single byte → [3]
  Output: [1, 1, 1, 2, 2, 3]

Escape Sequence:
  - 255 is reserved as escape marker
  - Literal 255 bytes encoded as [255, 255, 1]
  - Handled transparently in encode/decode


TWO-STAGE COMPRESSION PIPELINE
───────────────────────────────

Compression Process:
  1. Read input file (binary)
  2. Apply RLE preprocessing (if enabled)
     - Converts runs to compact format
     - Example: 10,000 bytes → 120 bytes (98.8% reduction)
  3. Apply Adaptive Huffman encoding
     - Generates variable-length binary codes
     - Highly effective on RLE output
  4. Write compressed bitstream
  5. Return statistics

Decompression Process:
  1. Read compressed bitstream
  2. Check format version (8-bit header)
  3. If Version 2 (RLE+Huffman):
     a. Apply Huffman decoding
     b. Apply RLE decoding
  4. If Version 1 (Huffman only):
     a. Apply Huffman decoding only
  5. Write decompressed data
  6. Return statistics


FILE FORMAT
───────────

Version 2 (RLE + Huffman) - NEW:
  Byte 0 bits:   [8 bits] Version = 2
  Bytes 1-2 bits: [16 bits] Number of chunks
  Bytes 3+:      Huffman-encoded data (from RLE preprocessed input)
  Last byte:     Padding bits (zeros) to byte boundary

Version 1 (Huffman only) - ORIGINAL:
  Bytes 0-1 bits: [16 bits] Number of chunks
  Bytes 2+:      Huffman-encoded data
  Last byte:     Padding bits (zeros) to byte boundary

Auto-Detection:
  - Reads first 8 bits to check for version number
  - If first 8 bits = version identifier (valid range)
    → Version 2 detected
  - Otherwise
    → Version 1 detected
  - Decompressor applies appropriate algorithm

ALGORITHM COMPLEXITY
────────────────────

RLE Encoding:
  Time Complexity:  O(n) - process each byte exactly once
  Space Complexity: O(n) - output can be up to same size
  
RLE Decoding:
  Time Complexity:  O(n) - expand each byte once
  Space Complexity: O(n) - expanded output size
  
Huffman (on RLE output):
  Time Complexity:  O(m log m) where m = RLE-encoded size
  Space Complexity: O(m) - tree and codes
  
Overall Pipeline:
  Time Complexity:  O(n + m log m) ≈ O(n + m log m)
  Space Complexity: O(n + m)


ERROR HANDLING
──────────────

RLE Module:
  - Empty input: Returns empty list
  - Single byte: Encoded as-is
  - Escape bytes: Handled transparently
  - Incomplete sequences: Graceful fallback
  
Compressor:
  - File not found: Exception with message
  - Permission denied: Exception with message
  - Disk full: Exception with message
  - Corrupted data: Graceful error message
  - Incomplete chunks: Recovered with warning


PERFORMANCE CHARACTERISTICS
────────────────────────────

Encoding Speed:
  RLE:      ~50 MB/s (linear processing)
  Huffman:  ~5-10 MB/s (tree operations)
  Combined: ~3-5 MB/s (depends on input)

Compression Ratio:
  Best case (highly repetitive):    0.2-1% of original
  Good case (moderate repetitive):  5-20% of original
  Average case (normal data):       30-50% of original
  Worst case (already compressed):  80-110% of original


WHEN TO USE RLE
───────────────

OPTIMAL FOR:
  ✓ Text files with repeated spaces/newlines
  ✓ Log files (often have repeated patterns)
  ✓ Source code (indentation, repeated keywords)
  ✓ Images with solid regions
  ✓ Database exports (often repetitive)
  ✓ Any data with runs of identical bytes

NOT OPTIMAL FOR:
  ✗ Already compressed files (ZIP, JPEG, MP3)
  ✗ Random or encrypted data
  ✗ When every byte is unique
  ✗ Very small files (overhead not worth it)

SYSTEM BEHAVIOR:
  → Automatically tries both approaches
  → Uses whichever is smaller
  → Marks format version for decompression
  → Seamless operation for user
